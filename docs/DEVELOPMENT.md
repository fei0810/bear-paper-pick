## 开发、使用与验收的分工

本仓库是 Skill 的唯一持续开发入口，维护指令、脚本、测试、公共文档与版本。开发和离线检查不需要维护者的 iCloud 项目。研究项目是使用者，保存种子、画像、候选、反馈、已推状态和阅读成果；可以有多个研究项目使用同一个 Skill。

安装目录保存某个版本的运行包，不作为第二个源码仓库。开发时可让 Agent 直接读取本仓库 SKILL.md，在独立数据目录验证；日常使用建议安装已验收的固定版本。源码提交不会自动更新已经复制安装的 Skill，需要显式升级并记录版本或提交 ID。升级更换工具文件，保留研究线数据；格式发生变化时按迁移说明执行。

运行时的连接只有明确的配置和数据接口：通过环境变量或配置文件提供服务设置，通过研究线路径提供输入和输出。个人路径记录在被 Git 忽略的 `.local-workspace.md`，不是代码依赖。当前私人配置仍在维护者的历史项目目录；后续更换位置只需更新本机配置路径。真实 Jev 运行还需要可用服务和合法 key，不能把离线可开发等同于离线可完成推荐。

新用户验收使用固定提交或运行包、独立配置和干净数据目录，按 [ACCEPTANCE.md](ACCEPTANCE.md)执行。它是单独的验收任务，不需要复制出另一个长期维护的产品仓库。原始记录可留在验收者的研究项目，公开仓库只收录脱敏且有权再分发的复现和结论。

## 推荐开发方式

在 Codex 中将本仓库作为独立本地项目打开；Claude Code 和其他 Agent 也从同一仓库入口接手。项目按产品划分，会话按具体任务划分。建议按需建立功能开发、问题修复、新用户验收、发布准备等会话，每个会话给出明确完成条件，结束时将决定、验证范围与待办更新回本文件和 CHANGELOG。此处是组织建议，不代表已经创建这些会话。

单人或不同 Agent 轮流工作时，复用一个本地仓库，每次开始先检查当前分支、提交和未提交改动，结束时保存可审阅提交。需要并行修改时，为各项工作使用独立分支和 worktree；每个 worktree 使用独立测试数据目录，避免代码已隔离却共同改写同一个研究状态。

研究项目中发现问题时，先记录使用的版本、输入、预期行为与实际结果，再把最小脱敏复现交回本仓库修复。改动通过相关检查后，用修复版本在原场景复测；日常研究切换到已验证版本。开发结论以仓库文件和 Git 为准，历史聊天是来源参考；切换 Agent 无须复制全部聊天或另建一套项目规范。

可给接手 Agent 的开场说明：

## 已实现的主流程

`fetch.py` 取数和验证元数据；`profile_snapshot.py` 维护结构化研究画像；`sift.py screen` 将固定规则预排的候选交给 Jev，默认最多 40 篇，单次上限 200 篇。筛选结果生成 `screening.json` 和 `review.md`。每个研究线目录复用缓存，预算之外的候选明确列为 deferred。

`screening.py` 校验本期画像、候选、远程输入指纹、typed answers 与排序记录，要求选题中的分歧说明。`sift.py validate/render/register` 使用同一筛选记录；digest 显示 Jev 判断和摘要句，回执绑定 `screening.json`。这是一致性和可追溯性检查，不是 API 来源的密码学证明或科学结论验证。

网络失败保存已完成请求和失败记录，主工作流不自动降级。修复后在新的输出目录重跑，相同输入复用缓存；若用户选择基础模式，记录原因。
